# 礼小记 2026 升级审计与增长路线图

> 审计日期：2026-07-11  
> 基线提交：`f582257`（`origin/main`），对应当前 App Store 线上 1.0  
> 工作分支：`upgrade/product-audit-20260711`  
> 调研范围：App 源码、测试、现有产品文档、商店素材、Apple 官方资料、中国区 App Store 竞品与评论

## 1. 结论先行

礼小记已经具备一个垂直工具的完整功能面，但还没有形成一个能持续获得下载、留存和口碑的产品闭环。当前最缺的不是更多功能，而是三件事：

1. **可信的数据生命周期**：只有 CSV 导出，没有可恢复备份、导入、迁移预检和真实同步校验。对于要保存数年的人情数据，这是购买和长期使用的前提。
2. **清晰且高频的核心价值**：当前首页主要展示本月收支，产品仍像一个礼金版记账 App。真正有差异的价值应是“下次该给谁回礼、回多少、什么时候准备”。
3. **可运营的增长系统**：App 上架近 5 个月仍是 1.0，只有 1 个评分，在核心关键词搜索中不可见，也没有版本节奏、评价触发、反馈入口或可用的质量门禁。

建议将下一阶段定位从“功能齐全的人情记账”调整为：

> **一个本地优先、长期可靠的回礼决策助手。** 先帮用户把旧账安全搬进来，再让用户在需要回礼时立即得到可信答案。

## 3. 当前项目的关键问题

### P0：发布前必须解决

#### 3.1 测试套件无法编译

`xcodebuild test` 在 `LiShangJiTests/ModelTests.swift:193` 和 `:198` 失败。测试仍读取已经删除的 `GiftEvent.eventCategory`，而模型已经改为字符串字段 `category`。主 App target 可以构建，但回归测试完全无法运行。

同时，App 最低系统为 iOS 17.6，测试 target 却配置为 iOS 26.0。这会让最低支持版本长期没有自动化覆盖。仓库也没有 CI、SwiftLint 或发布前脚本。

**验收标准：**

- 单元测试和 UI 冒烟测试在 CI 中可编译、可运行。
- 至少覆盖 iOS 17.6 兼容构建和当前 iOS 版本运行测试。
- 合并到主干前强制执行 build、test、StoreKit 购买/恢复购买冒烟测试。

#### 3.2 “已同步”并不代表数据真的已同步

`ICloudSyncService.swift:207-253` 只检查 iCloud 账户可用并获取 `userRecordID()`，随后就把状态显示为“已同步”。这不能证明 SwiftData 数据已上传、已下载或两台设备数据一致。`ICloudSyncView.swift:162-164` 进一步向用户宣称“以上数据已通过 iCloud 在您的设备间同步”，存在错误安全感。

同步开关只写入 `UserDefaults`，要求用户手动重启 App。项目没有开启/关闭同步时的数据快照、迁移预检、数量核对或失败回滚。

**验收标准：**

- 开启同步前自动生成可恢复快照。
- 展示可验证状态：本地最后保存、最近一次远端变更、待同步/异常，而不是仅凭账户状态显示“已同步”。
- 用两个设备/模拟器验证新增、修改、删除、冲突、离线恢复和关闭再开启。
- 同步失败时不丢本地数据，并提供用户可理解的恢复路径。

#### 3.3 没有可恢复备份和导入

代码只实现 CSV 导出；技术文档中的 JSON 快照恢复仍是规划。用户无法把导出的 CSV 导回 App，也无法从竞品、Excel 或旧纸质账本低成本迁移。`ClearDataView` 明确提示数据不可恢复，但没有先备份入口。

**建议第一优先交付：**

- 版本化 JSON 全量备份，包含稳定 ID、关系、账本、记录、提醒和设置。
- 恢复前预览、校验、去重、合并/覆盖策略和回滚快照。
- CSV 导入模板与列映射，支持常见竞品和 Excel 格式。
- 导出与备份默认免费。用户自己的数据不应被付费墙锁住。

#### 3.4 商店承诺与实际行为不一致

- 商店描述承诺“后台自动模糊”，但 `LiShangJiApp.swift:109-118` 只在用户开启应用锁后遮罩；默认状态下任务切换器仍可能显示金额。
- 隐私政策写“录音数据仅在本地处理，不会上传”，但 `Speech` 在不支持设备端识别时会回退到系统服务端识别。应准确说明由 Apple 语音识别服务处理的可能性，或强制只允许设备端识别。
- README 和三份核心文档使用“礼尚记”，App、隐私政策、StoreKit 使用“礼小记”，线上描述首行又写“礼尚记”。
- PRD 写 ¥9.9，StoreKit 本地配置为 ¥8，品牌常量版本永远写死为 `1.0`。

这些不只是文档问题，会影响审核、信任、客服和品牌搜索。

### P1：直接影响留存和付费

#### 3.5 核心产品仍是“看账”，不是“解决回礼”

首页展示本月收到、送出和最近记录，却没有把历史关系转成下一步行动。建议首页改为三层：

1. **今天要处理**：即将到来的婚礼/生日/节日，需要回礼或准备礼物的联系人。
2. **快速记一笔**：默认带出最近联系人、上次金额、常用类别和账本。
3. **本月概览**：收支统计降为次级信息。

联系人详情应突出“上次对方给我多少”“我最近一次回了多少”“尚未回礼的事件”，并允许一键按历史记录创建回礼。金额建议必须解释依据，可由用户调整，避免制造“算法替用户决定礼数”的不适感。

#### 3.6 付费边界不统一且可绕过

免费版限制 1 个账本、20 个联系人、3 个提醒，但限制主要写在页面按钮中。`RecordViewModel.swift:83-91`、OCR 和语音的批量联系人创建可以绕过联系人上限。付费规则应进入统一领域服务，而不是散落在 UI。

更重要的是，当前高级版把 iCloud 和数据导出放入付费权益。结合竞品差评，建议重新分层：

| 免费且建立信任 | 一次性买断高级版 |
|---|---|
| 无限基础记录、单账本、基础联系人、JSON 备份/恢复、CSV 导入导出、基础隐私保护 | 多账本、OCR 批量识别、语音批量录入、高级统计、家庭共享、智能回礼提醒、主题与批量整理 |

不要用“数据安全”逼迫购买。高级版应出售效率、协作和决策价值。

#### 3.7 新用户第一次打开就收到通知权限请求

`LiShangJiApp.swift:92-95` 在主界面首次出现时立即请求通知权限，此时用户尚未创建任何提醒，也没有理解通知价值。应在用户第一次设置生日/事件提醒时，以预授权页面解释具体收益后再触发系统弹窗。

#### 3.8 没有评分与反馈闭环

当前只有设置页的“给我们评分”，没有在成功完成高价值任务后触发。Apple 官方建议在用户完成任务、最可能满意时请求评分，且不要打断操作。

建议触发条件：完成首次恢复验证、成功录入第 5 或第 20 条、首次收到提醒并完成事件、完成一次批量导入。每个版本最多选择一个满意节点，并提供“先反馈问题”入口。

### P2：体验与品牌升级

#### 3.9 iPad 是放大的 iPhone，不是 iPad 应用

现有 iPad 截图中，Tab Bar、列表和小字号内容横跨 13 英寸画布，空间利用率低，交互距离过长。代码只有录入页和数字键盘读取 `horizontalSizeClass`，主导航没有 `NavigationSplitView`。

建议 iPad 使用侧边栏：总览、账本、联系人、提醒、统计、设置。列表与详情双栏显示；录入作为固定宽度 sheet；统计页限制内容宽度并提高图表信息密度。

#### 3.10 视觉完成度尚可，但品牌辨识度弱

现有 UI 清爽、金额可读、色彩克制，是可保留的基础。主要问题是：

- 首页、统计、设置大量使用同质白卡片，层级依赖卡片边界，缺少真正的品牌记忆点。
- App 图标更像通用钱包，无法快速传达“礼簿、关系、回礼”。
- Tab Bar 的大面积悬浮背景和多个悬浮加号在 iPhone 上抢占内容，也容易与系统导航层级竞争。
- 联系人页和设置页信息密度较高，但缺少“我下一步要做什么”的优先级。

建议保留朱砂红，但减少卡片数量，使用分组、留白和轻分隔线建立层级。首页只保留一个主行动区。为图标测试至少准备三种方向：礼簿印章、礼单折页、双向礼结；通过 Product Page Optimization 验证，不凭主观选最终方案。

#### 3.11 无障碍与动态字体只是文档承诺

UI/UX 文档要求 VoiceOver、金额朗读、Reduce Motion 和 Dynamic Type，但代码几乎没有语义化无障碍标签，也没有 `accessibilityReduceMotion`。项目中有大量固定宽高和固定字号。应补齐：

- 金额、方向、差额的完整朗读文本。
- 图表的文本摘要和可访问数据表。
- 大字体下录入、联系人、提醒和购买页的布局测试。
- Reduce Motion、Increase Contrast、Button Shapes、Voice Control。

## 4. 建议的新产品主线

### 4.1 北极星场景

> 用户收到邀请或准备参加事件时，在 10 秒内查到与对方的历史往来，并创建一笔有依据的回礼记录或提醒。

围绕这个场景建设以下闭环：

`导入旧账 -> 联系人去重 -> 自动形成往来时间线 -> 事件提醒 -> 显示历史依据 -> 一键回礼 -> 适时请求评价`

### 4.2 优先功能

| 优先级 | 功能 | 用户价值 | 增长价值 |
|---|---|---|---|
| P0 | JSON 备份恢复 + CSV 导入 | 敢于长期使用和迁移 | 降低差评，形成“数据不会被锁”口碑 |
| P0 | 同步可信状态与双设备测试 | 换机不慌 | 直接击中竞品最大痛点 |
| P0 | 测试/CI/迁移容错 | 更新不破坏旧数据 | 支撑稳定发版节奏 |
| P1 | 回礼待办与一键复用历史记录 | 从查账变成行动 | 提高事件前后的回访率 |
| P1 | 批量手动录入、表格粘贴、导入预检 | 婚礼现场高效录入 | 提升首日激活和高级版价值 |
| P1 | 联系人合并、别名、男/女方及家庭归属 | 解决真实脏数据 | 提升长期数据质量 |
| P1 | 隐藏金额模式 | 当面核对时保护隐私 | 可感知的差异点 |
| P2 | 家庭共享账本 | 夫妻/父母共同维护 | 自然邀请和口碑传播 |
| P2 | Widget / App Intent 快速记账 | 降低再次打开成本 | 提升复访 |
| P2 | 礼物/实物、图片、估值 | 扩展非现金场景 | 扩大使用频率 |

### 4.3 暂不优先

- **LBS 区域礼俗库**：内容维护和准确性成本高，当前没有用户反馈证明它比数据迁移更重要。
- **更多统计图表和年度报告**：低频工具的留存不靠更多图表，应先解决提醒和回礼行动。
- **Dynamic Island**：场景持续时间短，价值弱于 Widget 和 App Intent。
- **泛化 AI 聊天助手**：会稀释隐私和本地优先定位。先用结构化历史记录做可解释建议。
- **立即开发 Android**：成本过高。先通过开放备份格式、CSV 和家庭共享验证跨设备需求。

## 5. 90 天执行路线图

### 第 1-2 周：恢复可发布基线

- 修复测试编译，统一 deployment target，建立 CI。
- 品牌、版本、价格、隐私文案和商店描述统一为线上真实状态。
- 修复默认后台隐私遮罩，通知改为场景化请求。
- 为 ModelContainer 启动失败提供恢复界面，不再直接 `fatalError`。

**门槛：** 主 target 构建成功；全部自动化测试通过；旧版本数据升级和失败回滚可验证。

### 第 3-5 周：数据信任版本 1.1

- JSON 全量备份/恢复、CSV 导入、导入预检、去重。
- 同步状态改为可验证模型，完成双设备测试矩阵。
- 清空数据前强制提供备份选项。
- 在设置页增加问题反馈、诊断导出和明确的本地/云端状态。

**目标：** 导入成功率 >= 98%；恢复后的实体与关联校验 100%；同步测试不出现静默丢失。

### 第 6-8 周：核心体验版本 1.2

- 首页重构为“待处理、快速记录、概览”。
- 一键回礼：从联系人历史或提醒创建预填记录。
- 批量手动录入和表格粘贴。
- 联系人合并、别名和家庭归属。
- iPad 侧边栏和双栏详情。

**目标：** 首条记录完成率、首日 3 条记录完成率和 7 日回访率明显提升；手动单笔录入中位时间 < 10 秒。

### 第 9-12 周：增长版本 1.3

- 重做商店截图，第一张直接表达“查历史，知道这次该怎么回”。
- 标题/副标题/关键词覆盖“人情、礼金、随礼、份子钱、回礼、礼簿”。
- 对图标和首屏截图做 Product Page Optimization，一次只改变一个主要变量。
- 在满意节点请求评分，建立低评分/问题反馈处理流程。
- 为婚礼、春节、乔迁等不同意图建立 Custom Product Pages。

**目标：** 核心词自然可见性提升；产品页转化率持续提升；每个版本获得稳定的新评分，而非依赖一次性请求。

## 6. 指标体系

在不破坏“无广告、无追踪”承诺的前提下，先使用 App Store Connect、TestFlight 反馈、崩溃/诊断和可选匿名统计。若引入任何行为遥测，必须先明确数据最小化、保留周期、用户选择和隐私政策变更。

### 核心指标

- **北极星指标：** 每周完成“查看历史依据并创建回礼/提醒”的活跃用户数。
- **激活：** 安装后 24 小时内完成首条记录；7 天内完成 3 条记录或一次导入。
- **信任：** 启用备份比例、恢复验证成功率、同步错误率、数据丢失相关反馈数。
- **留存：** D7、D30，以及事件提醒后的 7 日回访。
- **付费：** 看到付费页、开始购买、购买成功；分别按入口分析，不只看总转化。
- **口碑：** 每版本新增评分数、低星问题分类、开发者回复时效。
- **效率：** 单笔录入时长、批量录入每条耗时、导入失败原因。

## 7. 上架与品牌建议

“礼小记”和“礼尚记”都已经存在同名或近同名竞品。当前 App 已以“礼小记”先于 2026 年 6 月出现的“礼小记：账本”上架，因此短期不建议仓促改名。建议：

1. 先统一仓库、应用内、隐私政策和商店描述，全部使用线上品牌“礼小记”。
2. App Store 标题采用“品牌 + 明确品类”的结构，并在 App Store Connect 验证可用性，例如“礼小记 · 人情礼金账本”。
3. 副标题不再重复口号，直接承接搜索与价值，例如“随礼回礼有据，数据本地保存”。
4. 品牌改名应另做商标、域名、社交账号和 App Store 名称可用性检查，不在一次 UI 更新中顺手完成。

现有关键词列表缺少“回礼、礼金簿、份子、红包、备份”等意图词，也没有把“本地优先、可迁移”转成截图证据。商店截图应展示真实工作流，而不是八张功能页平铺。

推荐截图顺序：

1. 查清往来，这次回礼有依据。
2. 纸质礼单批量识别，并可逐条校对。
3. CSV/备份轻松搬入搬出，数据不被锁住。
4. 联系人时间线，一眼看清收、送和差额。
