> 文档版本：1.0  
> 编制日期：2026-07-12  
> 线上基线：`main`，当前线上版本 1.0  
> 候选版本：1.2，分支 `upgrade/product-audit-20260711`  
> 适用范围：App Store / TestFlight 候选构建的上线前最终验收

## 1. 目标与发布原则

本计划用于验证礼小记从线上 1.0 升级到 1.2 后的数据安全、功能完整性、一次性买断权益、CloudKit 混合版本同步、隐私与文档一致性、性能和稳定性。

测试通过可以把风险降低到预先约定的发布门槛，但任何测试都不能从数学意义上保证软件在所有设备、系统和网络组合下零缺陷。这里的“可以上线”定义为：本计划全部 P0/P1 用例通过、没有未关闭的阻塞/严重缺陷、所有发布证据齐全，并由产品、研发和测试负责人共同签字。

### 1.1 产品术语

- 当前付费商品是非消耗型一次性买断，不是订阅，不得出现“按月/按年订阅”“自动续费”文案。
- 线上旧版指 App Store 生产版本 1.0，不以仅修改版本号的测试包代替。
- 新版指与准备提交审核完全相同的 1.2 Archive/TestFlight 构建。
- “iCloud 已开启”只表示容器启用了 CloudKit；不能把账户可用或一次远端通知描述为“所有数据已同步”。

### 1.2 Stop-Ship 发布阻塞条件

出现以下任意情况必须停止发布：

1. 任何升级、同步、恢复、导入操作造成数据数量减少、金额变化、关系丢失或无法恢复。
2. 线上 1.0 无法原地升级，或升级失败只能删除 App 解决。
3. 新旧版本同时使用时基础记录在任一端消失、重复、无法编辑，或删除传播无确定结果。
4. StoreKit 已扣款但未解锁、恢复购买失败、冷启动后权益丢失，或未购买用户错误解锁。
5. CloudKit Production Schema 未部署，或真实双设备同步矩阵未完成。
6. 隐私政策、用户协议、购买页、审核备注和实际代码行为不一致。
7. P0/P1 用例未执行、失败或缺少证据；存在未关闭的阻塞/严重缺陷。
8. Release Archive、签名、Bundle ID、CloudKit Container ID、Product ID 与线上配置不一致。
9. 迁移或核心流程超过性能红线，出现持续卡死、崩溃、看门狗终止或不可控内存增长。

### 2.1 当前已知的文档与实现冲突

以下问题必须在生成最终候选构建前解决，不能只通过修改测试预期绕过：

1. `docs/app-store-submission.md` 写免费版最多 1 本礼簿、20 个联系人、3 个提醒；当前 `EntitlementPolicy` 只明确限制多账本及 OCR/语音批量、高级分析、回礼助手。联系人和提醒额度必须以最终产品决策统一代码、购买页和审核备注。
2. 升级技术方案把 iCloud、备份、CSV 定义为免费数据能力；旧审核材料把 iCloud 同步、数据导出写成高级权益。数据可携带性不能在不同页面采用不同规则。
3. 关于页和商店材料存在“多端无缝”“换机不丢数据”等绝对表述。在 CK/MIX 真机矩阵完成前必须改为可证明的描述；完成后也不得承诺 CloudKit 永不失败。
4. 购买页必须始终表述为 Non-Consumable 一次性买断，所有“订阅”术语只能用于说明“非订阅、无自动续费”。

禁止使用开发者或真实用户的日常 iCloud 账号执行删除、清空、混合版本和冲突测试。每轮 CloudKit 测试前记录容器环境、zone、账号和初始记录数量。

### 3.3 构建与云环境

1. 旧版：从 App Store 下载线上 1.0，或使用与线上 commit、Bundle ID、entitlements 完全一致的签名构建。
2. 新版：上传到 TestFlight 的 1.2 Release Archive，不使用 DEBUG 权益开关。
3. Bundle ID：`com.xxl.LiShangJi`。
4. CloudKit Container：`iCloud.com.xxl.LiShangJi`。
5. StoreKit Product ID：`com.xxl.LiShangJi.premium`，类型必须为 Non-Consumable。
6. CloudKit 先在 Development 验证，再部署 Production Schema，最终混合版本测试必须使用 TestFlight/Production 环境。

### 3.4 网络条件

每个需要网络的核心模块至少覆盖：正常 Wi-Fi、蜂窝网络、弱网高延迟、断网、传输中切网、后台后恢复、CloudKit/App Store 服务临时失败。

## 5. 执行顺序

必须按顺序执行，后续阶段不能掩盖前一阶段失败：

1. 冻结候选 commit、版本号、Archive 和配置清单。
2. 执行静态检查、全量单元/集成/UI 自动化和 Archive。
3. 执行本地数据的全新安装、覆盖升级、失败恢复和降级保护。
4. 执行 StoreKit Sandbox/TestFlight 交易及全部高级功能。
5. 部署 CloudKit Production Schema，执行同版本和 1.0/1.2 混合版本双设备矩阵。
6. 执行权限、隐私、帮助、免责、升级说明和 App Store 文案验收。
7. 执行性能、压力、后台、弱网、耗电和 7 天 TestFlight 稳定性。
8. 汇总证据、关闭缺陷、复跑受影响回归集，完成发布签字。

### 15.2 稳定性浸泡

1. TestFlight 候选构建在至少 3 台设备运行 7 天。
2. 每天至少完成新增、编辑、删除、搜索、备份、前后台和一次网络切换。

4. 目标：0 崩溃、0 数据损坏、0 无法恢复错误；任何崩溃必须定位、修复并重新开始相关观察窗口。
5. 记录 TestFlight crash、hang、MetricKit、CloudKit 错误和用户可见异常。

## 16. 缺陷等级与回归规则

| 等级 | 定义 | 发布处理 |
|---|---|---|
| Blocker | 数据丢失/损坏、无法启动/升级、错误扣款、账号数据泄露 | 必须修复，停止全部发布流程 |
| Critical | 核心 CRUD/同步/恢复/购买不可用，稳定复现崩溃 | 必须修复并全量回归 |
| Major | 重要功能错误、严重 UI/无障碍问题、有可行绕过 | 原则上修复；延期需书面签字 |
| Minor | 不影响完成任务的轻微视觉/文案问题 | 可评估延期，但必须登记 |

修复迁移、Schema、写入、CloudKit、StoreKit、备份或权限问题后，必须复跑对应模块、全量自动化、真机升级和受影响的跨模块用例，不能只复跑失败用例。
